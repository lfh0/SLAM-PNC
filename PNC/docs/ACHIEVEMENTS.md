# 端到端局部规划器阶段成果

## 1. 文档说明

本文档记录项目当前已经完成并确认的设计成果。

状态说明：

- 本文所述内容是已经评审和冻结的技术方案；
- 当前不代表对应代码已经实现或通过实车验证；
- 实施任务、依赖与验收标准以 `docs/TASKS.md` 为准；
- 系统需求与接口约束以 `docs/REQUIREMENTS.md` 为准。

## 2. 已完成的总体设计决策

端到端局部规划器被拆分为三个大模块：

```text
模块一：基础工程改造
模块二：数据与模型训练
模块三：在线推理与部署
```

当前决定先完成模块一，在没有训练模型的条件下打通确定性局部规划闭环；模块一验收通过后再进入完整训练和在线推理接管。

冻结的总体边界为：

- 保留Super-LIO定位、A*全局规划和MPC控制；
- 保留MINCO作为传统方案、专家来源、对照基线和回退能力；
- 神经网络未来只替换局部轨迹生成模块，不直接输出底盘控制；
- 网络或确定性基线只输出最小局部轨迹变量；
- 完整 `RobotTrajectory` 由确定性轨迹适配器生成；
- 所有候选轨迹必须经过Safety Checker；
- MPC必须先支持10 Hz滚动参考更新，禁止每条局部轨迹触发完整重置；
- 推理超时、轨迹断流和输入异常必须进入独立安全降级链路。

### 3.1 F1：坐标、时间与车辆状态基础层

候选方案：

1. 各节点分别查询TF和odom；
2. 建立统一车辆状态与时空查询模块。

选定方案：建立统一车辆状态与时空查询模块。

理由：统一处理时间戳、TF、状态插值、数据过期和定位跳变，避免训练、推理、轨迹适配和安全检查分别维护不同逻辑。

冻结接口方向：

```text
输入：Super-LIO odom、TF、底盘速度/转角、车辆参数、查询时间
输出：直接复用 `/lio/robo/odom`、`/lio/cloud_imu` 及 `map -> world -> robot -> imu` TF
```

冻结TF结构：

```text
map
└── world
    └── robot
        └── imu
```

设计约束：

- `world -> robot` 由Super-LIO动态发布；
- `robot = IMU中心 = 车辆旋转中心 = 规划与控制参考点`；
- `robot -> imu`为单位变换；
- LIO估计链和Gazebo真值车模链保持独立，禁止发布绑定二者的TF；
- 后续模块直接使用Super-LIO消息的原始时间戳，不新增重复车辆状态节点。

独立验证：已在Super-LIO和Gazebo运行态检查话题frame、频率、延迟以及 `map -> robot/imu` TF可查询性。

### 3.2 F2：MPC任务与滚动参考控制层

候选方案：

1. 保留 `reset()` 并降低轨迹发布频率；
2. 更新轨迹时直接继承旧数组索引；
3. 分离任务状态与局部参考，新轨迹重新进行位置和航向联合匹配。

选定方案：方案3。

冻结接口方向：

```cpp
startMission(mission_goal)
updateLocalTrajectory(robot_trajectory)
cancelMission()
computeCommand(vehicle_state)
```

设计约束：

- `startMission()`只在真正的新导航任务开始时重置；
- `updateLocalTrajectory()`不修改全局终点、不清空任务状态、不触发起始航向调整；
- 新旧局部轨迹数组索引不直接继承，在新轨迹中重新匹配当前车辆；
- 使用位置、航向和路径进度联合匹配，避免回环及平行轨迹误匹配；
- 使用完整轨迹复制和互斥保护，避免轨迹回调与控制计算读到半更新状态；
- 阻塞式停车改为由控制周期推进的非阻塞状态机。

独立验证：使用人工完整Map轨迹，以10 Hz更新直线、圆弧和不同长度轨迹，检查任务状态、匹配点、控制频率和输出连续性。

### 3.3 F3：统一轨迹协议与确定性基线层

候选方案：

1. 直接截取A*路径；
2. 直接截取MINCO轨迹；
3. A*路径截取、轻量平滑和曲率限速。

选定方案：方案3；MINCO继续作为传统回退和训练专家来源。

F3已实现：新增`robot_trajectory_msgs/RawLocalTrajectory`协议和独立`raw_local_planner`包。正式输入已改为MINCO发布的`/trajopt/global_trajectory`；节点以10 Hz结合`/lio/robo/odom`和任务目标，完成轨迹去重/重采样、单调进度匹配、曲率与终点联合限速，并将Map轨迹转换为观测时刻`robot`坐标系。MINCO已负责几何平滑，因此F3不再二次平滑。7项核心单元测试全部通过。

### 3.4 F4实现结果

新增独立`trajectory_adapter`包，将`RawLocalTrajectory`按历史里程计观测时刻转换到Map坐标，按当前时间裁剪过期段并重采样，输出字段完整的`RobotTrajectory`到`/safety_checker/candidate_trajectory`。适配器保留F3在MINCO参考上选择的起点，不再注入当前车辆位姿连接段，以便MPC看到真实跟踪误差。5项适配器测试通过；F4不执行碰撞检查，输出接入F5前不得用于无人值守运行。

F1～F4联调辅助已补充：`full_navigation.launch`一键启动前端规划、F3、F4和MPC；F3发布`/local_planner/raw_path_map`，F4发布`/trajectory_adapter/debug_path`；适配器输出扩展为31点约3秒，MPC预测步数调整为20；新任务首点触发原地方向对齐，最小对齐角速度调整为0.12 rad/s。

运行态诊断发现并修复F3首点与车辆位置不一致导致的低速抖动：现在首点与当前车辆重合，后续轨迹才向前展开；F2/F3/F4回归测试保持全部通过。

统一原始轨迹协议：

```text
observation_stamp
frame_id = base_link(t_obs)
dt = 0.2 s
15 × [x, y, v]
confidence
stop_probability
contains_mission_goal
source
sequence_id
```

第一版选择绝对局部坐标 `[x,y,v]`，暂不使用位置增量，原因是更容易可视化、调试并避免增量累计误差。

路径处理采用单调进度匹配：新任务时全局搜索，后续在上次进度附近匹配并沿弧长向前截取，避免在回环或平行路段选择错误分支。

速度由任务速度上限、曲率横向加速度限制、末端制动距离和速度变化率共同确定。

独立验证：使用直线、圆弧、S弯、回环和平行路径，检查坐标转换、单调进度、时间语义和任务终点标记。

### 3.4 F4：延迟补偿与轨迹适配层

候选方案：

1. 把整条历史轨迹平移到车辆当前位置；
2. 只转换到Map但保留已经过期的轨迹前段；
3. 历史位姿转换、时间裁剪、执行状态预测和连续连接。

选定方案：方案3。

冻结处理顺序：

```text
使用T_map_base(t_obs)转换到map
 -> 计算t_exec-t_obs
 -> 按时间插值并裁掉过期段
 -> 预测t_exec车辆状态
 -> 生成0.2～0.5秒短连接段
 -> 按时间平滑和重采样
 -> 计算完整RobotTrajectory字段
```

连接方案第一版采用三次/五次多项式或曲率连续样条，不采用简单线性连接；当连接误差超限时拒绝轨迹，不通过拉长连接段强行接入。

轨迹以时间作为主参数，同时生成MPC需要的弧长字段。yaw由平滑曲线切向确定，曲率优先通过解析导数计算，并保证 `omega = v * curvature`。

明确禁止整体平移历史轨迹来对齐当前车辆，因为这会改变轨迹相对地图和障碍物的真实位置。

独立验证：注入0、50、100、200和500 ms延迟，验证坐标转换、过期段裁剪、执行状态拼接、低速数值退化和轨迹不回跳。

### 3.5 F5：确定性Safety Checker

候选环境检查方案：

1. 直接使用原始点云；
2. 只使用二维代价地图；
3. 二维距离场为主，原始点云或动态时序占用为补充。

选定方案：方案3。

候选车辆碰撞方案：

1. 只检查轨迹中心点；
2. 只在轨迹采样点放置车辆矩形；
3. 使用完整footprint并检查相邻点之间的swept volume。

选定方案：方案3。

检查顺序按照计算代价从低到高：

```text
格式与有限数值
 -> 时间、TF和数据新鲜度
 -> 起点与新旧轨迹连续性
 -> 运动学限制
 -> 静态footprint碰撞
 -> swept-volume碰撞
 -> 动态时空碰撞
 -> 末端制动距离
```

Safety Checker只负责准入和结构化拒绝原因，不承担复杂轨迹修复，不允许把碰撞轨迹简单改为全零速度轨迹。

独立验证：人工注入NaN、Inf、过期、跳变、各类动力学超限，以及车体中心、车角和轨迹点之间的障碍物，验证拒绝原因和检查耗时。

### 3.6 F6：轨迹管理、唯一来源与安全降级层

候选轨迹源方案：

1. 通过ROS remap让多个规划器直接发布同一控制话题；
2. 独立轨迹管理器订阅各候选来源，只发布一个最终控制参考。

选定方案：方案2。

内部候选话题分别保留：

```text
/minco/trajectory
/baseline/trajectory
/neural/trajectory
```

唯一最终输出：

```text
/controller/reference_trajectory
```

候选降级方案：立即急停、无限复用旧轨迹、分级降级状态机。选定分级状态机：

```text
NORMAL
 -> DEGRADED
 -> DECELERATING
 -> STOPPED
 -> EMERGENCY
```

制动优先沿最后一条仍安全的轨迹降低速度；剩余轨迹不足时按当前车辆状态生成受约束短时停车轨迹；只有定位严重异常或明确即时碰撞风险才进入紧急制动。

状态转换必须具有迟滞。严重故障恢复后不能收到一条正常轨迹就自动高速恢复，应等待连续健康数据，必要时要求上层或人工重新开始任务。

独立验证：模拟多发布源、轨迹断流、连续拒绝、规划进程退出和定位失效，检查唯一输出、轨迹有效期、状态转换和受控制动。

## 5. F1实施结果

F1已完成以下运行态核验与必要配置修正：

- 冻结 `robot = IMU中心 = 车辆旋转中心 = 规划与控制参考点`；
- 冻结规划TF链 `map -> world -> robot -> imu`；
- 保持LIO估计链和Gazebo真值链独立；
- 确认 `/lio/robo/odom` 约200 Hz、平均延迟约2 ms；
- 确认 `/lio/cloud_imu` 约10 Hz、平均延迟约7 ms；
- 确认 `map -> robot` 和 `map -> imu`可查询；
- MPC轴距已由0.5 m修正为当前仿真车辆的0.4 m；
- 确认不新增重复的车辆状态或TF节点。

当前 `map -> world` 的Z轴2 m偏移需在后续BEV高度处理前确认其地图标定含义，但不阻塞F1定位链使用。
